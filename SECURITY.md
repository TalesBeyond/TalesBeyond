# Hearthbound — Security Posture

A dedicated, severity-ranked audit of the live Supabase project backing
cloud-mode Hearthbound — host-credential security, cross-table/DM-data
isolation, and abuse/availability resistance — done as part of `REQ-006`
(`requirements/Done/REQ-006-Live-Table-Security-Hardening.md`). Kept
separate from `PITFALLS.md` (general bugs/gotchas found during feature
work) so this can stay a focused, revisitable security record, though it
follows the same status-legend convention.

This document was produced by a code/migration-level review only — no
direct access to the live Supabase project's dashboard or CLI. Anything
that can only be confirmed by looking at the live project itself is
called out in the **Live Supabase dashboard checklist** below rather than
marked as verified.

**Status legend:** ✅ Fixed · 🟡 Needs a decision (not a bug) · ⬜ Planned / not yet fixed

## Findings

| # | Severity | Category | Finding | Status | Fix / Next step |
|---|----------|----------|---------|--------|------------------|
| 1 | High | Abuse & availability | `create_table` (`supabase/migrations/20250101000003_functions.sql`) had no cap on how many tables one auth identity could create — a script could spam it to bloat the database (tables, layers, islands, players, invite_codes rows) or run up project cost, with nothing in this schema stopping it. | ✅ | Fixed in code (REQ-006 Slice 3, `supabase/migrations/20250101000026_security_hardening.sql`): `create_table` now rejects a new table once the calling identity already hosts 20. **Live since 2026-09-30** (applied and tested by the host). |
| 2 | High | Credential security | The live project's password policy (mirroring `supabase/config.toml`) accepted any 6-character password with no complexity requirement — e.g. `123456` was valid for a host account. | ✅ | Fixed in code (REQ-006 Slice 2): `config.toml` now requires an 8-character minimum with upper+lower+digit. **Mirrored on the live project's dashboard by hand and tested, 2026-09-30** (config.toml changes don't reliably auto-apply to an already-live hosted project, per `REQ-003`'s own history). Existing host accounts created under the old 6-character policy are grandfathered in; Supabase doesn't retroactively invalidate them. |
| 3 | Medium | Abuse & availability | `join_table`'s invite code was 6 characters from a 32-symbol alphabet (≈1.07 billion combinations). Supabase's built-in `[auth.rate_limit]` settings only govern its own auth endpoints (sign-in, sign-up, anonymous sign-ins, token refresh, OTP) — they do **not** apply to `join_table`'s RPC calls, so nothing in this stack throttles a script guessing codes in a loop. | ✅ | Fixed in code (REQ-006 Slice 3, `supabase/migrations/20250101000026_security_hardening.sql`): codes are now 8 characters (≈1.1 trillion combinations) — `generate_unique_code()` (server) and `generateInviteCode()` (client fallback, `src/utils/inviteCode.js`). Previously issued 6-character codes keep working until regenerated. **Live since 2026-09-30** (applied and tested by the host). |
| 4 | Medium | Credential security | No CAPTCHA is configured on host sign-up/sign-in (`[auth.captcha]` in `config.toml` is present but fully commented out) — nothing slows a scripted sign-up/credential-stuffing attempt beyond Supabase's generic per-IP auth rate limits. | 🟡 | Needs a real hCaptcha or Cloudflare Turnstile account (site key + secret) that only the host can create — deferred as a follow-up until that account exists. See Open Question Q1 in `REQ-006`. |
| 5 | — | Data isolation | Re-verified 2026-09-30 through migration `055`: all 19 tables have row-level security enabled (confirmed by grepping every `create table` against every `alter table ... enable row level security` across `supabase/migrations/*.sql`). **Table data:** `tables`, `invite_codes`, `players`, `maps`, `entities`, `layers`, `islands`, `entity_dm_data`, `user_preferences` as originally audited; `entities`' SELECT policy was since narrowed so unrevealed traps are host-only (finding #9). `custom_assets` (`036`), `audio_tracks` (`038`) and `drawings` (`052`) follow the same shape: members of the table read, only its host inserts/updates/deletes. The seven Default-catalog tables (`catalog_weapons`, `catalog_items`, `catalog_monsters`, `catalog_audio`, `catalog_dice_images`, `catalog_dice_models`, `catalog_dice_skins`, `042`–`047`) are read-only to `anon`/`authenticated` with no write policy, so only the service-role admin script can change them. DM notes, mob droppables and mob sheets live in the host-only-readable `entity_dm_data` table (`015`, `030`). **Storage:** six buckets. `token-art` and `map-backgrounds` (`004`) restrict uploads to a folder named after a table the uploader belongs to, and `048` blocks anonymous sessions from uploading at all; since `055` the app no longer uploads to them (images are built-in icons or `img:<sha-256>` fingerprints exchanged browser to browser). `table-audio` (`038`, tightened by `048`) accepts uploads and deletes only from a signed-in, non-anonymous host, into their own table's folder, audio types only, 10 MB each. `catalog-images`, `catalog-audio`, `catalog-models` (`042`, `045`, `047`) are public-read with no upload policy (admin-write only). **Realtime:** the publication (`050`) only adds tables already listed here; Realtime applies each table's SELECT policy per subscriber. **No gap found — no fix needed.** Accepted limitation: every bucket is public-read, so anyone holding a file's exact URL can fetch it; paths are random file names under a table id, and nothing in them is DM-secret. | ✅ | None — re-verify again if new tables or storage buckets are added. |
| 6 | — | Secrets handling | Re-verified as part of this audit: no `service_role` key appears anywhere in the client bundle or repo (grepped). `src/lib/supabaseClient.js` only ever uses `VITE_SUPABASE_PUBLISHABLE_KEY`, the anon-equivalent key that's safe to ship client-side. The one place the service-role key is used, `scripts/catalog-admin.mjs` (Default-catalog admin, run by hand in Node), reads it from `SUPABASE_SERVICE_ROLE_KEY` in `.env` and refuses a key that looks public; it is never imported by the app. `.env` is gitignored; only `.env.example` (with blank values) is tracked. **No gap found — no fix needed.** | ✅ | None. |
| 7 | High | Abuse & availability | A `/code-review` of finding #1's fix (the 20-table host cap) found it was a non-atomic check-then-insert — concurrent `create_table` calls from the same identity could all read a count under 20 before any insert committed, letting more than 20 through. The same review also found `tables.host_auth_id` had no supporting index, so the cap's count query was a full table scan on every call. | ✅ | Fixed in code (REQ-007, `supabase/migrations/20250101000027_host_table_cap_hardening.sql`): `create_table` now takes a `pg_advisory_xact_lock` keyed on the caller's identity before the count, and `tables_host_auth_id_idx` was added. **Live since 2026-09-30** (confirmed by the host). |
| 8 | Medium | Abuse & availability | The same `/code-review` found the 20-table cap had no way back: once a host's total ever-created table count reached 20, `create_table` blocked them forever, since there was no delete/archive flow to free a slot. A legitimate long-lived host (or anyone who'd just tested/experimented enough) could hit a permanent, unrecoverable lockout. | ✅ | Fixed in code (REQ-007, same migration): a new host-only `delete_table` RPC lets a host permanently delete one of their own tables — cascading through existing FKs and best-effort cleaning up its Storage images — from a new Delete action on Landing's "Your tables" list, immediately freeing a cap slot. **Live since 2026-09-30** (delete flow tested by the host). |

| 9 | Medium | Data isolation | Trap tokens (`20250101000028_traps.sql`) must be invisible to players until the DM reveals them. `entities`' SELECT policy let every seated member read every row, so hiding a trap in the UI alone would have exposed its position and numbers to anyone opening devtools or the Realtime feed. | ✅ | Fixed in code: the migration narrows `entities`' SELECT policy so an unrevealed trap is host-readable only (guest tables get the same guarantee from the DM's broadcast filter, `toGuestBroadcastAction` in `GameView.jsx`). Un-revealing a trap in cloud mode is a delete + re-insert (`hideTrapRemote`), because Realtime sends no event when a row stops being visible to a subscriber. **Migration still needs to be applied to the live project** — see checklist below. |

## Live Supabase dashboard checklist

Things this audit could not verify directly (no live project access) —
the host should confirm each of these on the actual hosted project:

- [ ] **`20250101000034_trap_size.sql` applied live.** Lets a trap be 5x5 (`entities.size` was capped at 4 for every kind; the migration allows 5 for traps only). Until it's applied, placing or resizing a trap to 5x5 works on screen but fails to save at the database in cloud mode; 1x1 to 4x4 traps are unaffected.
- [ ] **`20250101000033_day_night_override.sql` applied live.** Adds `tables.day_night_override` (the DM's manual day/night phase). Until it's applied, the manual phase works on screen but fails to save at the database in cloud mode; the clock itself (032) is unaffected.
- [ ] **`20250101000032_game_clock.sql` applied live.** Adds `tables.game_clock` (the in-game clock) and `islands.day_night`. Until it's applied, joining and playing are unaffected, but setting the clock or an island's day/night mode works on screen and fails to save at the database in cloud mode.
- [ ] **`20250101000031_island_conditions.sql` applied live.** Adds `islands.conditions`. Until it's applied, setting an island condition works on screen but fails to save at the database in cloud mode (placing and editing islands otherwise still works).
- [ ] **`20250101000030_mob_sheet.sql` applied live.** Adds `entity_dm_data.mob_sheet`, where a monster's DM-only character sheet is stored (host-only under the table's existing RLS). Until it's applied, placing monsters still works, but editing a monster's sheet tabs fails at the database in cloud mode.
- [ ] **`20250101000028_traps.sql` and `20250101000029_trap_damage_type.sql` applied live (in that order).** 028 adds the `trap` entity kind and its columns, and replaces `entities`' SELECT policy so unrevealed traps stay host-only. 029 adds the trap's damage-type column. Until both are applied, placing a trap in a cloud-mode table fails at the database (the `kind` check rejects `'trap'`, then the missing column).
- [x] **`20250101000027_host_table_cap_hardening.sql` applied live.** *(Confirmed and the delete flow tested by the host, 2026-09-30.)* Same reason as below — this migration (advisory-lock cap fix, index; and later REQ-007 Slice 2's delete-table capability) exists as a file only until it's run against the live project.
- [x] **`20250101000026_security_hardening.sql` applied live.** *(Confirmed and tested by the host, 2026-09-30.)* This migration (8-character invite codes, 20-table host cap) exists as a file but is not applied to the live project automatically — run it via the CLI (`supabase db push`) or paste it into the SQL Editor, the same way prior migrations in this project's history have needed manual application (see `PITFALLS.md` #13/#14).
- [x] **Password policy mirrored.** *(Set in the live dashboard and tested by the host, 2026-09-30.)* Once REQ-006 Slice 2 lands in `config.toml`, manually set the equivalent minimum length (8) and character requirements (upper+lower+digit) in **Authentication → Providers → Email** on the live project. `config.toml` values are not guaranteed to auto-apply to an already-live hosted project (confirmed the hard way during `REQ-003` — "Confirm email" needed the same manual mirroring).
- [ ] **Anonymous sign-in rate limit is live.** Confirm **Authentication → Rate Limits** actually enforces a per-IP cap on anonymous sign-ins (config.toml specifies 30/hour) — this is the only thing currently limiting how fast an attacker can mint fresh identities to work around the new create_table/invite-code protections.
- [ ] **"Confirm email" stays disabled.** Already required for this app's no-confirmation host sign-up flow (`REQ-003`) — verify it hasn't been re-enabled by a project settings change or reset.
- [ ] **No `service_role` key has ever been exposed.** Double-check no commit, log, or support ticket has ever pasted the live project's `service_role` key; rotate it if there's any doubt.
- [ ] **CAPTCHA provider (recommended follow-up).** Consider creating a Cloudflare Turnstile (or hCaptcha) account and enabling **Authentication → Attack Protection → CAPTCHA** — deferred in this pass (see Finding #4); flag when ready so REQ-006's Open Question Q1 can be picked up.
- [ ] **Auth rate-limit values still make sense.** Spot-check **Authentication → Rate Limits** against `config.toml`'s `[auth.rate_limit]` block (`sign_in_sign_ups`, `token_refresh`, `token_verifications`, `web3`) — these were never tuned for this app specifically, just left at Supabase's defaults.
